# XenonFin 0.4.2 menu recovery and text presentation

The user has now confirmed the previous text flicker issue is fixed; version 0.5 preserves this text path while adding a reserved video region. The following records the rendering investigation and 0.4.2 recovery.

The user confirmed actual 0.4 MP3 playback on Xbox 360 through XeLL: music works, the blue background is stable, and white text flickers. This change preserves the audio decoder/output, raw lwIP HTTP, Jellyfin APIs and controller operations. New presentation must be validated on that hardware.

## Cause established from source

1. `main.c::draw()` entered `xf_console_begin()`, printed the entire page, then called `xf_console_end()`. Now-playing redrew on a 500 ms timer. Rendering was not called from decoder or HTTP callbacks, although main unnecessarily called an additional music tick after each redraw.
2. In 0.4, `console_batch.c::xf_console_begin()` called libXenon's `console_clrscr()`. The pinned console owns a private `console_fb` pointing at the **currently scanned-out** surface read from `D1GRPH_PRIMARY_SURFACE_ADDRESS` (`0x6110`). The clear writes background pixels directly to that surface. Each subsequent console glyph writes foreground/background pixels into the same surface. There is no off-screen render target or swap in that path.
3. LibXenon normally flushes the entire framebuffer after clearing and after every character. The 0.4 `--wrap=memdcbst` adapter deferred those explicit console flushes until the end of the draw. It did **not** provide a backbuffer or prevent cache eviction/writeback while clear/glyph stores were in progress. A full framebuffer is larger than CPU cache. Erased pixels can reach display memory before replacement glyphs, exposing an incomplete frame.
4. This explains **text-only** flicker: background pixels are replaced with the same blue, whereas white text becomes blue until it is redrawn. The timer triggers repeated exposure; successful decoding/audio output does not make this presentation safe.

Inspected upstream sources at [pinned libXenon revision](https://github.com/Free60Project/libxenon/tree/c32c813c3d630ae922f83395ee4509b0468af71d): `drivers/console/console.c` (`console_init`, `console_clrscr`, `console_pset32`, `console_putch`, stdout hook), `drivers/xenos/xe.c` (`Xe_SetFrameBufferSurface`) and `drivers/xenos/xenos.h`. The existing Xenos surface API establishes support for changing the scanout address of a tiled BGRA8888 surface without replacing the video mode or initializing the GPU command/shader pipeline. AVIVO frame count/update/flip bits were checked against [Linux v6.6 r500_reg.h](https://github.com/torvalds/linux/blob/v6.6/drivers/gpu/drm/radeon/r500_reg.h): `0x60a4`, surface-pending bit 2 at `0x6144`, horizontal-retrace enable bit 0 at `0x6148`.

## 0.4.1 regression and 0.4.2 recovery

The user tested 0.4.1: the menu stopped updating, but **B still returned to XeLL**. This establishes that input and the main loop were alive; the apparent freeze was in presentation. That build put `xf_console_ready()` behind a pending swap. `xf_console_frame_poll()` permanently set `fault = 3` when the display address differed, the pending bit stayed asserted, or the frame count did not advance within 500 ms. A rejected initial swap also set a permanent fault. With any fault, `main.c` continued polling controllers but never called `draw()` again. This was a regression introduced by the presentation change.

No register capture is available from that console, so the precise failed register condition is **not established**. The Linux AVIVO register definitions and host mocks did not validate Xbox retrace acknowledgement. Version **0.4.2** removes all runtime dependence on those registers rather than weakening a fence and reusing potentially visible buffers.

## Current implementation: framebuffer compatibility presentation

- `console_batch.c` captures the existing printf pages and direct text into a complete character grid. It preserves the original font, BGRA colors, detected dimensions, overscan, wrapping and two-row scroll. Unbuffered stdout preserves printf/direct-character ordering; description height uses the captured cursor.
- `console_frame.c` maintains two CPU-side tiled surfaces with cached character grids. Glyphs are drawn only when their cells differ from that surface's saved cells. Each surface is capped at 8 MiB, 16 MiB total; geometry remains the original rounded-32-pixel pitch up to 1920×1080. These surfaces are **never installed as display scanout** in 0.4.2.
- `framebuffer.c` uses the original framebuffer address and cached mapping that libXenon's `console_init()` already uses. It does not write GPU registers, change video mode/scanout/flip control, or read frame-count/update registers. The first complete frame is copied to that framebuffer. Later complete frames are compared against the previous CPU-side image in 128-byte cache lines; **only changed lines** are copied and cache-flushed. There is no separate background erase pass. Static titles remain in place, and shortened values receive completed replacement pixels, including spaces.
- Presentation completes when those bounded CPU copies and cache synchronization finish. The compositor's next poll acknowledges that completed copy directly. There is no hardware-acknowledgement deadline to permanently suppress menu updates, no retrace spin and no added sleeps.
- This is a compatibility path, **not an atomic page flip**. A scan can overlap changed-region copies, particularly when replacing a whole menu. It targets the observed text disappearance by eliminating erase-and-repaint of unchanged text, while avoiding the unvalidated hardware swap that froze 0.4.1. Tear-free swapping remains future hardware investigation, not a claim of this recovery build.
- During page drawing, stdout is captured. Outside drawing, its framebuffer hook is disabled so library logs cannot overwrite cached UI text on the shared original surface; `vfs_console_write()` still emits its serial log. Network/DHCP diagnostics printed inside their page are captured as before. Exit restores the original hook; the video address and mode never changed.
- `ui_clock.c` retains 250 ms visible statistics updates and immediate controller/data events. Identical frames do not publish any pixels. Audio/HTTP/DHCP/controller ticks remain in the existing cooperative loop; drawing does not invoke them. The audio, decoder, music API, network and HTTP implementation sources are unchanged. No audio-path delay was introduced.

## Console regression test

Download [xenonfin-xell-music-fix.elf](../dist/xenonfin-xell-music-fix.elf), check `dist/SHA256SUMS`, rename to **xenon.elf**, and boot with the same USB/XeLL procedure and display mode as the working build. The title must say **0.4.2**. Graphics/controller must show **Text: changed regions; GPU flip wait disabled.** Keep the unchanged [0.4 ELF](../dist/xenonfin-xell-music.elf) as rollback.

1. With no music running, leave the Graphics/controller page visible and navigate several sections. Confirm stable text, colors, margins, no blank frames and immediate selection changes. Confirm LB/RB and Up/Down visibly change the selection before initializing Network. This existing static page provides a no-audio comparison.
2. Initialize Network, verify the DHCP diagnostics, enter the numeric server IP/port, test the server and sign in. Check masked typing and long-title/details wrapping. No credential or streaming code changed.
3. Browse Music → artist → album → track and play a known song. Leave Now playing visible for several minutes. White labels/titles must stay continuously visible; position and byte/frame counters should update about four times per second, without flashing or partial glyphs. Music must remain continuous and at the same speed/pitch as 0.4.
4. Pause/resume with A or Start, skip with Left/Right, and stop with X. Check the existing controls and progress. On stop, unchanged statistics should stop causing surface updates. A short audio DMA drain is existing behavior, not a new delay.
5. B returns to Libraries while music continues. Browse/page/select details during playback, then Back/View returns to Now playing. Text must stay stable during network requests, and playback/controller input must remain responsive.
6. Revisit Graphics with music playing to compare static text against the changing player page. Repeat after stopping the music. If an issue remains, record whether it affects static or changing text, console model, cable/display mode, screen, controls still responding, and whether audio continues. Reboot and compare the original 0.4 asset under identical conditions.

## Cloud validation

The same Xenon toolchain builds the XeLL ELF without warnings/errors. Native host suites pass normally and with AddressSanitizer/UndefinedBehaviorSanitizer. New tests exercise the real character compositor with a simulated live display during each write (including pending/visible immutability, shortened-text erasure, static glyph reuse, identical-frame suppression, timeout/wrap handling), the stdout hook/direct-character adapter, and the actual native compatibility presenter together with the compositor, mapped onto RAM (font pixels, overscan, 1080p bounds, changed-region copies, unchanged text, shortened values and over 100 frames without any GPU acknowledgement). The backend test rejects reads of frame-count/update/flip registers and provides no GPU-write symbol, so reintroducing a swap dependency fails the test/link. The UI clock test produces exactly four scheduled frames per second and permits immediate input changes.

`python3 tests/native_server.py --music` passes real Jellyfin 10.10.7 authentication/browsing and MP3 direct/transcoded playback, pause/resume, next/previous, natural advance, stop/reporting and transcode cleanup through the existing native sources and test-only TCP/audio bridge. These regressions protect the working stream/player path; they cannot validate actual Xbox scanout or establish that menu responsiveness and visible text stability have been restored on console.
