# XenonFin 0.4.1 text presentation fix

The user confirmed actual 0.4 MP3 playback on Xbox 360 through XeLL: music works, the blue background is stable, and white text flickers. This change preserves the audio decoder/output, raw lwIP HTTP, Jellyfin APIs and controller operations. New presentation must be validated on that hardware.

## Cause established from source

1. `main.c::draw()` entered `xf_console_begin()`, printed the entire page, then called `xf_console_end()`. Now-playing redrew on a 500 ms timer. Rendering was not called from decoder or HTTP callbacks, although main unnecessarily called an additional music tick after each redraw.
2. In 0.4, `console_batch.c::xf_console_begin()` called libXenon's `console_clrscr()`. The pinned console owns a private `console_fb` pointing at the **currently scanned-out** surface read from `D1GRPH_PRIMARY_SURFACE_ADDRESS` (`0x6110`). The clear writes background pixels directly to that surface. Each subsequent console glyph writes foreground/background pixels into the same surface. There is no off-screen render target or swap in that path.
3. LibXenon normally flushes the entire framebuffer after clearing and after every character. The 0.4 `--wrap=memdcbst` adapter deferred those explicit console flushes until the end of the draw. It did **not** provide a backbuffer or prevent cache eviction/writeback while clear/glyph stores were in progress. A full framebuffer is larger than CPU cache. Erased pixels can reach display memory before replacement glyphs, exposing an incomplete frame.
4. This explains **text-only** flicker: background pixels are replaced with the same blue, whereas white text becomes blue until it is redrawn. The timer triggers repeated exposure; successful decoding/audio output does not make this presentation safe.

Inspected upstream sources at [pinned libXenon revision](https://github.com/Free60Project/libxenon/tree/c32c813c3d630ae922f83395ee4509b0468af71d): `drivers/console/console.c` (`console_init`, `console_clrscr`, `console_pset32`, `console_putch`, stdout hook), `drivers/xenos/xe.c` (`Xe_SetFrameBufferSurface`) and `drivers/xenos/xenos.h`. The existing Xenos surface API establishes support for changing the scanout address of a tiled BGRA8888 surface without replacing the video mode or initializing the GPU command/shader pipeline. AVIVO frame count/update/flip bits were checked against [Linux v6.6 r500_reg.h](https://github.com/torvalds/linux/blob/v6.6/drivers/gpu/drm/radeon/r500_reg.h): `0x60a4`, surface-pending bit 2 at `0x6144`, horizontal-retrace enable bit 0 at `0x6148`.

## Implementation

- `console_batch.c` now captures the existing printf pages and direct text into `console_frame.c`'s complete character grid. It preserves the original font, BGRA colors, detected dimensions, overscan, wrapping and bounded two-row scroll. Unbuffered stdout preserves printf/direct-character ordering; the cursor used for description height comes from the captured grid.
- `framebuffer.c` owns two separate, 64 KiB-aligned tiled surfaces, each capped at 8 MiB (16 MiB total, static allocation). Supported geometry is the original rounded-32-pixel pitch, up to 1920×1080, with padded-height bounds. The current linked image's total static memory ends below 24 MiB; the existing audio DMA allocation remains in libXenon's low-memory BSS section.
- Pixels are only changed in the free backbuffer. Every buffer retains its own prior character grid; unchanged glyphs are reused after the two surfaces are first populated. Spaces erase shortened text off-screen. Identical frames cause no glyph drawing, cache flush or surface flip.
- After **all** clears/glyphs finish, the completed surface is cache-flushed and synchronized. The adapter clears horizontal-retrace flipping and queues the primary surface address for vertical retrace. It polls update-pending and frame-count registers cooperatively; the former frontbuffer cannot be reused until a retrace has occurred and the update is acknowledged. No live-buffer copy is used.
- A 500 ms acknowledgement watchdog retains both complete buffers on failure instead of guessing which is safe to overwrite. Audio/network/controller polling continues; presentation stops on that fault. If the first page appears but navigation never updates, report that symptom and video mode and use the unchanged 0.4 ELF for rollback. Physical register behavior is a console test, not proven by MMIO mocks.
- Original `console_init`, `xenos_init`, USB/audio initialization and diagnostics remain. During a page draw stdout is captured; outside it the original console hook logs to the boot surface, which is never one of the two managed UI surfaces. There is no global cache-flush interposition. Exit restores the boot surface/address and previous flip-control value.
- `ui_clock.c` limits visible playback/network/request statistics to **250 ms** intervals. Static screens need only input/data events, and identical frames are skipped. Input and completed metadata still request immediate frames, with dirty events retained during pending swaps. Decoder/network ticks run in the normal main-loop service phase; drawing never invokes them. No additional audio-path delay or sleep was added; the existing main-loop poll interval is unchanged.

## Console regression test

Download [xenonfin-xell-music-fix.elf](../dist/xenonfin-xell-music-fix.elf), check `dist/SHA256SUMS`, rename to **xenon.elf**, and boot with the same USB/XeLL procedure and display mode as the working build. The title must say **0.4.1**. Keep the unchanged [0.4 ELF](../dist/xenonfin-xell-music.elf) as rollback.

1. With no music running, leave the Graphics/controller page visible and navigate several sections. Confirm stable text, colors, margins, no blank frames and immediate selection changes. This existing static page provides a no-audio comparison.
2. Initialize Network, verify the DHCP diagnostics, enter the numeric server IP/port, test the server and sign in. Check masked typing and long-title/details wrapping. No credential or streaming code changed.
3. Browse Music → artist → album → track and play a known song. Leave Now playing visible for several minutes. White labels/titles must stay continuously visible; position and byte/frame counters should update about four times per second, without flashing or partial glyphs. Music must remain continuous and at the same speed/pitch as 0.4.
4. Pause/resume with A or Start, skip with Left/Right, and stop with X. Check the existing controls and progress. On stop, unchanged statistics should stop causing surface updates. A short audio DMA drain is existing behavior, not a new delay.
5. B returns to Libraries while music continues. Browse/page/select details during playback, then Back/View returns to Now playing. Text must stay stable during network requests, and playback/controller input must remain responsive.
6. Revisit Graphics with music playing to compare static text against the changing player page. Repeat after stopping the music. If an issue remains, record whether it affects static or changing text, console model, cable/display mode, screen, controls still responding, and whether audio continues. Reboot and compare the original 0.4 asset under identical conditions.

## Cloud validation

The same Xenon toolchain builds the XeLL ELF without warnings/errors. Native host suites pass normally and with AddressSanitizer/UndefinedBehaviorSanitizer. New tests exercise the real character compositor with a simulated live display during each write (including pending/visible immutability, shortened-text erasure, static glyph reuse, identical-frame suppression, timeout/wrap handling), the stdout hook/direct-character adapter, and the actual tiled/native backend with mocked MMIO/cache (font pixels, overscan, 1080p bounds, flush-before-presentation contract, flip bits and retrace acknowledgement). The UI clock test produces exactly four scheduled frames per second and permits immediate input changes.

`python3 tests/native_server.py --music` passes real Jellyfin 10.10.7 authentication/browsing and MP3 direct/transcoded playback, pause/resume, next/previous, natural advance, stop/reporting and transcode cleanup through the existing native sources and test-only TCP/audio bridge. These regressions protect the working stream/player path; they cannot validate actual Xbox scanout or establish that visible flicker has disappeared on console.
